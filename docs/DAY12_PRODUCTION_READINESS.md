# Zyngram Day 12 Production Readiness Report

**Scope:** `zyngram-day10` repository only. No earlier Zyngram projects were imported.
**Assessment:** Code review, backend regression suite, local MongoDB import, normalized-collection/index verification, and local API smoke checks. Target selected: MongoDB Atlas + Render. The supplied `mongodb://localhost:27017` is local to the developer machine and is not reachable from Render.
**Decision:** **NO-GO for public production launch.** Mongo-backed local demonstration and migration are implemented. Atlas networking/credentials, a truly transactional/normalized application repository, private object storage, a real recharge provider, and hosting credentials/domain remain prerequisites.

## Local database and migration verification (2026-10-07)

- The local API reports `ready: true`, `storage: mongodb`, revision `181`, and `transactions: false`. This verifies local connectivity only; the standalone MongoDB topology is not production-ready.
- `npm run verify:mongodb` passed: the migration receipt exists, all 27 source-backed/derived collections match the current canonical state, and an ADMIN session survived a new Node process. The previous read-only relationship audit checked 221 populated references without broken references. Current local counts include 28 Users, 13 Customers, 6 franchise-owner reference records, 49 UserLocations, 8 Franchises, 18 Orders, 6 OrderAttribution records, 12 CommissionLedger entries, and 7 Employees. Only 2 of the 6 franchise-owner references are linked to user accounts; the other 4 remain explicitly `UNLINKED` and need verified owner accounts before production.
- `npm run migrate:mongodb -- --dry-run` passed against the JSON migration source. That source currently has fewer records (21 Users, 12 Orders, 6 Employees) than the live local MongoDB state. **Do not rerun the one-time importer against the existing database or treat the older JSON source as a fresh production snapshot.**
- Customers and franchise-owner accounts are currently role-based records in `Users`; they are not separate `Customers` and `FranchiseOwners` MongoDB collections. Production schema normalization and Atlas migration remain incomplete.

## Security and test status

Existing tests cover registration/login, inactive account checks, franchise assignment/scope, customer order ownership, unmapped/low-accuracy locations, backend price control, commission idempotency, employee scope, document access, reports and audit behavior. Day 12 tests add recharge validation, amount persistence, duplicate request handling, and recharge commission calculation.

The backend now rejects wildcard/missing production CORS configuration and refuses production startup with the local demo administrator password. These are guardrails, **not** a security certification. The login and registration rate limiters use an in-memory per-instance store; use a shared store before scaling beyond the single Render instance. Before go-live, also perform HTTPS/TLS setup, secret rotation, rate-limit/abuse testing, durable session design, backup/restore rehearsal, dependency scanning, independent penetration testing and incident-response setup.

## Go-live blockers

1. Replace the synchronous aggregate snapshot and mirrored collections with a normalized repository whose order, attribution, commission and wallet changes commit in MongoDB transactions. Transactional snapshot/mirror persistence is an interim guardrail, not the normalized repository. Run on MongoDB Atlas replica-set topology and add rollback/reconciliation tests.
2. Rehearse backup/restore and migration on an Atlas staging database; verify counts before cut-over.
3. Configure account verification/recovery, session revocation/expiry policy and abuse controls.
4. Move employee documents to private object storage and test authorization using production-like policies.
5. Decide whether mobile recharge is a demo or a real product. Real service requires an approved operator/provider API, payment flow and callback/reconciliation handling.
6. Provision Atlas and Render, set the Atlas URI using Render's secret environment-variable UI (never in chat or source control), configure domains, TLS, backups, monitoring and alerting; then run the deployment procedure in `DEPLOYMENT.md`.
7. Re-run all automated tests and execute the manual security scenarios in the deployment checklist against staging before production approval.
